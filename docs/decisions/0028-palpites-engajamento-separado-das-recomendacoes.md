# ADR 0028 — Palpites como engajamento, separados das recomendações de valor

## Status

Accepted (2026-06-18) — **abre o arco de palpites (#313 → #314/#315/#316)** prometido pelo ADR 0029 ("**0028 está reservado** pro arco de palpites (#313)"). **Preserva integralmente o motor de valor dos ADRs 0015–0019** (mercados/seleções, edge segmentado por mercado, stake) — palpites são um domínio **aditivo e disjunto** que nunca os toca. **Apoia-se no ADR 0025** (gate Tier 3: corners/cards inviáveis end-to-end no Brasileirão) e no **ADR 0017** (versionamento de prompt por cartucho) para encaixar palpites como um cartucho próprio. **Respeita a fronteira `lib/ai/predict.ts` do ADR 0027** (única porta da LLM): o gerador de palpites passa por `predict.ts` só para logar custo/tokens, sem importar SDK.

> **Escopo:** este ADR é **produto + dados + IA**, mas estritamente do lado de **engajamento**. Nenhuma de suas decisões altera a feature de recomendações. Onde houver tensão entre "dar credibilidade ao palpite" e "contaminar o motor de valor", a resolução é **sempre** a favor de manter os domínios separados.

## Contexto

A tabela `predictions` (`db/schema.ts:254`, `pgTable("predictions", ...)`) é construída em torno de colunas do motor de valor: `impliedProbPct` (`:292`), `edgePct` (`:293`), `stakeUnits` (`:297`, `.notNull().default("1")`), além de `confidencePct` (`:286`), `minimumOdd` (`:289`) e `oddAtRecommendation` (`:290`). Cada predição é uma **recomendação de valor**: mercado + seleção + linha + stake, ou `pass`, com Yield segmentado (ADR 0018/0019). É a feature séria, e o CLAUDE.md ("O que NÃO fazer") proíbe contaminá-la — não mutar predições passadas, não furar a fronteira de `predict.ts`.

O pedido do #313 é o **oposto** em espírito: um **palpite** é diversão/engajamento — um chute de placar, "vai ter cartão vermelho", "vai dar mais de 9 escanteios". Não tem edge, não tem stake, não tem Yield. Misturá-lo em `predictions` (com colunas de valor nulas) apodreceria a semântica da tabela e arriscaria que qualquer query/agregação de Yield o varresse junto. Logo: **schema próprio + cartucho de prompt próprio**, aditivos, nunca cruzados.

O timing é bom porque o **gate Tier 3 já foi parcialmente descarregado**. O mercado `correct_score` está seedado (`db/migrations/0030_seed_correct_score.sql:12-37`: 16 seleções `cs_0_0`..`cs_3_3`, `is_active=true`/`is_graduated=false`, admin-only por ADR 0025) e **tem regra de settlement funcional** (`lib/settlement/rules/correct_score.ts:33-57`). Já corners/cards continuam **inviáveis end-to-end** (ADR 0025): sem odds em nenhum provider pro Brasileirão, e o normalizador de `/fixtures/events` da api-football é **goal-centric** — `toNormalizedFixtureEvents` faz `if (ev.type !== "Goal") continue;` (`lib/providers/sports-data/api-football/adapter.ts:541`), de modo que `NormalizedFixtureEventsSchema` (`lib/providers/sports-data/types.ts:90-100`) só expõe `goals`/`assists`. Não há dado de settlement para cartão nem escanteio. Isso desenha a fronteira: **placar exato é liquidável; cartão vermelho / escanteios entram "só por diversão"**.

## Decisão

**1. Palpites são um domínio aditivo e disjunto.** Schema próprio (`palpite_sets` + linhas de palpite, migration nova — `#314`), espelhando a forma de FK de `predictions` no que faz sentido: `matchId` → `matches.id`, `userId` → `users.id`, ambos `uuid().notNull().references(..., { onDelete: "restrict" })` (cf. `predictions` em `db/schema.ts:258-263`). **Divergência deliberada:** `predictions` carrega `aiCallId` **notNull** (`db/schema.ts:264-266`); palpites são gerados por LLM mas o vínculo de custo vive no `palpite_set` (não na linha individual), e a auto-geração pode falhar silenciosamente — então o FK para `ai_calls` deve ser **nullable** lá, não `notNull`. **Nenhuma coluna de valor** (`edge_pct`, `stake_units`, `implied_prob_pct`, `odd_*`) existe no schema de palpites; a UI **nunca** exibe edge / prob. implícita / stake / Yield.

**2. Passa por `predict.ts` só para logar.** A geração de palpites roteia por `lib/ai/predict.ts` (única porta da LLM, ADR 0027) **exclusivamente** para registrar custo/tokens em `ai_calls` (`provider`/`model`/`inputTokens`/`outputTokens`/`costUsd`/`status`, `db/schema.ts:235-244`). Nenhum cálculo de edge (ADR 0018) é executado no caminho de palpite. O motor de valor não pode ser contaminado, nem por dependência de código nem por dado.

**3. Flag `settleable` por tipo de palpite.** Cada tipo de palpite declara se é liquidável:

- **Placar exato** — `settleable: true`. Liquida por **comparação direta** dos params estruturados `{home, away}` com o placar regulamentar de 90', **sem** o limite de grade 0–3×0–3 do mercado `correct_score`. Um palpite `4-1` é perfeitamente válido e liquida. O placar de 90' vem do campo `NormalizedFixtureResult.regulationScore` (`lib/providers/sports-data/types.ts:50`, ET/pênaltis **excluídos** — extraído nos adapters, ex. `football-data-org/adapter.ts:265` via `score.regularTime`), convertido por `resultDataFromRegulationScore(rs)` (`lib/settlement/schemas.ts:75`). A comparação `{home, away}` é própria do tipo, **não** reusa `correctScoreRule` (cujo `if (homeScore > 3 || awayScore > 3) return "lost"`, `correct_score.ts:52-55`, presumiria a grade).
- **Cartão vermelho / escanteios** — `settleable: false`. Sem dado de settlement nos providers (corolário do `if (ev.type !== "Goal") continue` em `adapter.ts:541`; sem odds, ADR 0025). **Nunca** criam outcome, **nunca** entram no cron de settlement — honra o princípio "prefer skip over silent wrong settle". Adicionar um tipo liquidável novo (que exija provider de stats / SportMonks) **exige novo ADR** (gate Tier 3 do CLAUDE.md permanece de pé).

**4. Acompanhar onde der.** Tipos liquidáveis ganham badge **acertou/errou** + taxa de acerto histórica (mesma forma de query newest-first que `getPredictionHistoryForMatch`, `lib/db/queries/predictions.ts:91`, com `.orderBy(desc(createdAt), desc(id))` em `:109`). Tipos "fun" ficam **sinalizados como não-liquidáveis** na UI (sem badge de resultado, sem taxa).

**5. Auto-geração na entrada do jogo (`#315`).** Se ainda não houver palpite para `(matchId, userId)`, gera **idempotente** na entrada, via **Haiku 4.5** (`claude-haiku-4-5`, `lib/ai/models.ts:80-89`, low-temp — o registry já fixa `temperature: 0.3`), passado como `modelOverride` ao `predict.ts` (`predict.ts:68/245`). **Bucket de rate-limit separado:** os dois limiters de análise (prefixos `ratelimit:analyze` / `ratelimit:analyze:admin`) são montados em `getLimiters` (`lib/rate-limit.ts:78/86`), e `checkAnalysisRateLimit` (`:108/125`) só ramifica entre eles por role, consumindo a cota de **20/dia** das análises (`DEFAULT_USER_LIMIT = 20`, `:28`); palpites **não podem** drenar essa cota, então usam um terceiro `Ratelimit` com prefixo próprio (ex. `ratelimit:palpites`) sobre o mesmo Redis. A geração é **fire-and-forget com falha silenciosa** — porém ciente de que a página do jogo é Server Component (`app/match/[id]/page.tsx:60`) e **não** dispara `"use server"` actions no render; um promise não-aguardado no render serverless é frágil (pode ser morto ao retornar a resposta). O disparo deve vir de um child cliente (via uma action dedicada de palpite, irmã de `analyzeMatch` em `app/actions/predictions.ts`) ou de uma chamada server explicitamente aguardada e tolerante a falha — **não** de um promise solto no render.

**6. Regen sob demanda.** Reusa o mesmo gerador, passando os palpites anteriores como **contexto de exclusão** (não repetir o mesmo chute). Continua idempotente por geração.

**7. Histórico via "ver palpites anteriores" (`#316`).** Afordância explícita, **não** área colapsável — preferência declarada do dono (contrasta com `PreviousAnalyses`/`MatchCollapsible` de `#204`, que é colapsável). Ordem newest-first determinística, espelhando o tiebreak `desc(id)` da query de predições.

## Alternativas consideradas

1. **Palpites dentro de `predictions` com colunas de edge/stake nulas** — rejeitado: apodrecimento semântico de uma tabela cujo `stakeUnits` é `notNull().default("1")` (`db/schema.ts:297`); qualquer agregação de Yield ou query de recomendação varreria palpites junto, contaminando o motor de valor (ADR 0018/0019) — exatamente o que o CLAUDE.md proíbe.
2. **"Só por diversão" puro, zero settlement em qualquer tipo** — rejeitado: o placar exato **já é liquidável** hoje (`regulationScore` + comparação `{home, away}`) sem custo de provider novo; abrir mão disso joga fora a credibilidade barata de um badge acertou/errou. Liquida-se o que dá; o resto fica honestamente marcado como não-liquidável.
3. **Reenquadrar palpites como "valor de verdade", restrito a tipos que têm odds** — rejeitado: colapsa de volta na feature de recomendações (precisaria de edge/overround/stake e dos mercados dos ADRs 0015–0019), matando o propósito de engajamento e duplicando o motor de valor.

## Consequências

- **(+)** Motor de valor (ADR 0018/0019) fica **intocado**: zero coluna de edge no schema de palpites, zero cálculo de edge no caminho de geração, nenhuma agregação de Yield enxerga palpite. A separação é estrutural, não convencional.
- **(+)** Custo **desprezível**: ~US$0,002 por conjunto no Haiku 4.5; ainda assim **rastreável** em `ai_calls` como qualquer outra chamada, porque passa por `predict.ts` (ADR 0027 preservado).
- **(+)** Placar exato ganha credibilidade real (badge + taxa histórica) sem nenhum provider novo nem nova odd — só `regulationScore` (`types.ts:50`) + comparação estrutural.
- **(−)** O cron de settlement ganha um **caminho dedicado** só pros liquidáveis (placar): precisa filtrar por `settleable=true` antes de tocar em qualquer palpite, e jamais materializar outcome para os "fun". Mais uma ramificação a manter coerente com o resto do settlement.
- **(−)** **Landmine registrada (auto-run):** fire-and-forget na entrada do jogo é frágil em serverless. A página é Server Component (`page.tsx:60`) e não invoca `"use server"` actions; um promise não-aguardado pode ser morto ao retornar a resposta. A auto-geração tem de ser disparada de um child cliente ou de uma chamada server tolerante a falha, **com guard de idempotência** por `(matchId, userId)` antes de gastar token.
- **(−)** **Bucket de rate-limit novo:** os limiters de análise são montados em `getLimiters` (`rate-limit.ts:78/86`) com prefixos `ratelimit:analyze`/`:admin`, e `checkAnalysisRateLimit` (`:125`) só escolhe entre eles por role; palpites exigem um terceiro `Ratelimit`/prefixo sobre o mesmo Redis para **não** consumir a cota de 20/dia das análises (`rate-limit.ts:28`). Esquecer isso fura o teto das análises de valor.
- **(−)** **Slot de UI em DOIS branches:** `<PalpitesPanel/>` entra antes de `<AnalysisPanel/>` tanto no mobile (`app/match/[id]/page.tsx:301-314`, mesma coluna `flex flex-col gap-3` após os `OddsCard`) quanto no desktop (`DesktopMatch`, onde odds e análise vivem em wrappers separados do grid 2-col — inserção antes do `<div className="pb-6">`, `:390`). Não dá pra fazer só num lugar.
- **(−)** **Migration:** o número **0033 já está tomado** (enum→text de `ai_calls.provider`, ADR 0027/#231); a migration do #314 sai pelo **próximo índice livre via `pnpm db:generate`** (hoje **0034**), nunca hand-numbered.
- **(−)** **Gate Tier 3 segue de pé:** qualquer tipo liquidável novo (cartão/escanteio via `/fixtures/statistics` ou SportMonks) **exige ADR novo** — este ADR habilita só o que já tem dado (placar), não abre a porta para o resto.
- **(+)** Polimento visual da região destacada fica para o `#316` sob `/impeccable`, herdando os tokens da fundação (ADR 0029) — apresentação-only, sem tocar a lógica deste ADR.
