# ADR 0038 — Gate de edge determinístico no `predict.ts`: a disciplina de 5pp vira invariante de código

## Status

Accepted (2026-07-06) — issue #489 (ADR-first; Report 03 rec. 5 / Fase B; plan-gate adversarial: 1 rodada → rework de 2 blockers + 5 should-fix). Converte a **única regra de disciplina do produto** — "só recomenda se o edge ≥ piso do mercado" — de compliance-de-prompt (o LLM se auto-policia) para **invariante de código** enforçada no `predict.ts` após o parse Zod. Fecha o achado 3 do Report 03 (miscalibração indetectável: um edge computado de 3.2pp é persistido e mostrado como aposta). Complementa o ADR 0037 (baseline Poisson): 0037 ancora o número do modelo; este garante que o número só vira **aposta autorada** quando bate o piso. Não toca o firewall, o grade-my-bet (aposta do usuário), nem o registro Palpite (ADR 0028).

> **Escopo:** IA (motor de análise) — 1 gate no `predict.ts` (rebaixa a recomendação pra `pass`) + **reuso** do campo `minEdgePp` que já existe no `MarketDescriptor` (#290, hoje piso de prompt/view — este ADR o REPROPÕE como fonte também do gate) + `SCORER_MIN_EDGE_PP` promovido a export de `lib/odds/scenario.ts` (fonte única). SEM migration, SEM tabela nova, SEM mudança de schema. **FORA de escopo:** Dixon-Coles MLE (rec. 6), Kelly (rec. 7) — gated na calibração; remover a regra de piso do prompt (fica como guia soft — belt-and-suspenders); um flag/coluna de "downgraded" (a auditoria é reconstruível sem migration, ver Decisão 4).

## Contexto

Report 03 achado 3: a disciplina de edge é enforçada **só no prompt** — o `SYSTEM_PROMPT` do over/under (`lib/ai/markets/over_under/prompt.ts:9`) manda "recomende SOMENTE se confidence − implícita normalizada ≥ 5pp; senão pass". O código **computa** o edge (`predict.ts:962-965`: `edge = recModelProb − impliedPct`, de-vigado por seleção, ADR 0018) e o **persiste/exibe/dá stake** (`:1069`, `computeStakeUnits` `:975`), mas **nunca veta**: se o LLM emite uma recomendação com edge 3.2pp, ela é gravada como aposta, entra no Yield e aparece pro usuário. O LLM vê a implícita no input e pode ancorar nela — então um edge sub-piso escapa.

A constante já existe: `MIN_EDGE_PP = 5` (`lib/odds/scenario.ts:9`, importada pelos prompts de match_result/double_chance/correct_score; o over_under hardcoda "5" pinado por teste). O piso do scorer é **8** (`independent_binary`, implícita de TETO `1/odd` cru — margem não-removível, ADR 0025). E o `MarketDescriptor` já carrega `minEdgePp?: number` (#290) — hoje consumido só pelo PROMPT e pela VIEW (`lib/view/analysis.ts:334`: `descriptor?.minEdgePp ?? MIN_EDGE_PP`), 8 no scorer/assist, `undefined` (⇒ 5 via fallback) no resto. **Este ADR liga um TERCEIRO consumidor a esse mesmo campo: o gate.**

Por que ADR (curto): **(1)** muda o que é PERSISTIDO (uma recomendação do LLM pode virar `pass` por decisão de código) — auditabilidade; **(2)** o edge do código ≠ o edge do prompt em N-vias (`confidence_pct` pode ≠ `selectionProbs[recomendado]` em 1X2, `predict.ts:948-952`) — precisa nomear qual número corta; **(3)** repropõe o `minEdgePp` de piso-de-prompt pra fonte-do-gate (e promove `SCORER_MIN_EDGE_PP` a fonte única); **(4)** afeta o "best bet" (um mercado sub-piso deixa de concorrer) — decisão de produto.

## Decisão

**1. GATE no `predict.ts`: recomendação com edge PERSISTIDO abaixo do piso do mercado → rebaixada pra `pass`, deterministicamente, após o parse Zod.** O edge que decide o gate é o do lado que o LLM recomendou, computado dos mapas `impliedByKey`/`modelProbByKey` (`predict.ts:955-965`). Se **(a)** `recommendation ≠ pass`, **(b)** o edge é MENSURÁVEL (`!= null`), e **(c)** o edge ARREDONDADO (`edgePctRounded`, o MESMO valor congelado que staking e a UI mostram) é **`< piso`**, então o `side` efetivo vira `"pass"`. O gate corta o **edge do CÓDIGO** (`edgePct`, de-vigado por seleção, ADR 0018) — o número que é persistido, exibido, dá stake e ranqueia — porque gatear o número que a gente ACIONA é o invariante honesto ("nenhuma aposta autorada exibe um edge abaixo do piso"). Em N-vias (1X2) esse número pode divergir do `confidence − implícita` que o prompt pediu; a assimetria é **aceita e deliberada** — o edge de-vigado por-seleção é a verdade do ADR 0018, e é o que a gente mostra e aposta.

**2. PISO POR MERCADO: reusar `descriptor.minEdgePp`, resolvido com fallback — `descriptor.minEdgePp ?? MIN_EDGE_PP` (IDÊNTICO à view).** O gate NÃO faz um read cru de `descriptor.minEdgePp` (que é `undefined` em TODO mercado partition → o gate morreria justo neles). Resolve `cartridge.descriptor.minEdgePp ?? MIN_EDGE_PP`, o MESMO padrão da view (`analysis.ts:334`): partition (over_under/match_result/btts/double_chance/**correct_score**/over_under_alt) → `undefined` → **5**; `independent_binary` (scorer/assist) → **8**. **Fail-open num descriptor esquecido** = piso 5 (nunca gate morto silencioso). **Fonte única, sem drift (corrigido neste ADR):** `SCORER_MIN_EDGE_PP` vira export de `lib/odds/scenario.ts` (era `const` privada em `_scorer_shared/prompt.ts`); o descriptor (`minEdgePp: SCORER_MIN_EDGE_PP`, era literal `8`) E o prompt do scorer leem o MESMO símbolo. O comment do campo `minEdgePp` é atualizado de "piso de PROMPT, não gate de código" pra incluir o gate.

**3. NUNCA rebaixa em edge NÃO-MENSURÁVEL.** `edge === null` (board incompleto/degradado — `impliedByKey[side]` ausente, `predict.ts:955`; ou o cartucho omitiu a chave, `:961`) é **incerteza de medição, não edge-abaixo-do-piso**. O gate exige `edge !== null` — um edge nulo mantém a recomendação do LLM e o `edgePct: null` honesto de hoje. Rebaixar o não-mensurável mataria recs legítimas em board degradado (e, na prática, uma rec de board degradado já tem `oddAtRec=null`, `:954` — não é aposta settleable de Yield de qualquer forma). Fronteira **ESTRITA** (`< piso`, não `≤`): edge exatamente no piso (5.00) PASSA, casando o "≥ 5pp" do prompt; contra o valor ARREDONDADO (`edgePctRounded`), então a decisão do gate NUNCA diverge do `edge_pct` visível (o mesmo invariante que staking já pina em `predict.ts:967-972`).

**4. IMPLEMENTAÇÃO: reatribuir `side` via um `rawSide` separado — a row de pass rebaixada fica IDÊNTICA a um pass genuíno; auditoria SEM migration.** A ordem é o ponto (o edge do gate depende do lado, mas o lado depende do gate): **(i)** `const rawSide = output.recommendation`; **(ii)** computa `rawEdge`/`rawEdgeRounded` do lado `rawSide` a partir de `impliedByKey`/`modelProbByKey`; **(iii)** `const side = isBelowEdgeFloor(rawSide, rawEdgeRounded, piso) ? "pass" : rawSide`. A partir daí as expressões EXISTENTES `side === "pass" ? null : …` (`:954-965`) recomputam `oddAtRec`/`impliedPct`/`recModelProb`/`edge` = `null` quando gateado, e `selectionId` (`:981`) e `stakeUnits` (`edge=null → 1u`) seguem. O `edge` é computado DUAS vezes de propósito (o `rawEdge` só decide; o `edge` de `:962` já vê `side` gateado e dá null) — não há mecanismo "reatribui antes de :954" que funcione (rebaixar antes zeraria o `rawEdge` e o gate nunca dispararia). Na persistência: `recommendation: side` (era `output.recommendation`, `:1059`) e `minimumOdd: side === "pass" ? null : …` (`:1063` — um pass, inclusive gateado, não tem minimum_odd). **PRESERVADO pra auditoria:** `rationale`/`keyFactors`/`confidencePct` independem de `side` e sobrevivem; o `rationale` pró-lado + `recommendation = pass` + as rows de `prediction_selection_odds` (candidate set com `modelProbPct`, persistidas INCLUSIVE em pass, `:998-1012`) tornam o rebaixamento **reconstruível** (o edge sub-piso é recomputável do PSO). Nenhuma coluna nova, nenhum flag — a discrepância É o rastro.

**5. "BEST BET" ranqueia PÓS-gate; a badge "Melhor aposta" some quando o topo é pass.** O gate roda DENTRO do `predict()`, então o fan-out (`best-bet.ts`) e o sort (`sortBestBetEntries`, `components/best-bet-results.tsx:38` joga `isPass` pro fundo) veem a row já rebaixada. Um mercado cujo melhor lado tem edge < piso vira `pass` → cai da disputa — que é EXATAMENTE o certo (surfar como "melhor aposta" algo que não bate o piso é o próprio achado 3). Como o gate torna o "jogo inteiro em pass" mais frequente, a UI passa a **suprimir a badge "Melhor aposta" quando o topo do ranking é pass** (`best-bet-results.tsx:94` → `highlighted={!best.rank.isPass}`) — "nenhuma aposta acima do piso" é a resposta honesta, não um pass cravado como o melhor. O prompt-rule de piso **permanece** (guia soft): o LLM ainda tenta se policiar (menos recs sub-piso descartadas); o gate é o backstop determinístico — belt-and-suspenders, não substituição.

## Alternativas consideradas e rejeitadas

1. **Gatear `confidence_pct − implícita` (o número exato do prompt) em vez do edge de-vigado persistido** — rejeitado: iguais em over/under, divergem em 1X2 (`confidence_pct` ≠ `selectionProbs[rec]`); o número que a gente PERSISTE/EXIBE/APOSTA/RANQUEIA é o edge de-vigado. Gatear um número que não persistimos deixaria uma aposta com `edge_pct` visível < piso passar — o exato bug a fechar.
2. **Reatribuir `side="pass"` ANTES do cálculo do edge** — rejeitado: infazível (zeraria o `rawEdge` que decide o gate → gate nunca dispara). O `rawSide` separado (Decisão 4) é o mecanismo correto.
3. **Read cru de `descriptor.minEdgePp` (sem fallback)** — rejeitado: `undefined` em todo partition → `edge < undefined` é `false` → gate morto nos mercados do achado 3. `?? MIN_EDGE_PP` (o padrão da view) é obrigatório.
4. **Patch só na coluna `recommendation` no insert** — rejeitado: cria row-quimera (pass com selectionId/odd/edge/stake/minimum_odd) que quebra a exclusão do Yield e os ramos `isPass`. Reatribuir `side` reusa a lógica de pass-shape (Decisão 4).
5. **Rebaixar também em edge não-mensurável (conservador)** — rejeitado: incerteza de medição ≠ abaixo do piso; mataria recs legítimas em board degradado (Decisão 3).
6. **Mover `MIN_EDGE_PP` pra `staking.ts`** — rejeitado: o piso (5) e as bandas de stake (8/12) são números semanticamente independentes (nada a sincronizar), e mover churn ~14 importers + um `lib/odds` alcançável por client component. Fica em `scenario.ts`; o gate importa de lá.
7. **Coluna/flag `downgraded_by_gate`** — rejeitado por escopo: exigiria migration; a auditoria já é reconstruível (rationale + PSO). Follow-up se o dono quiser o flag explícito.
8. **Manter o "best bet" ranqueando no edge PRÉ-gate** — rejeitado: surfar como "melhor aposta" um mercado que não bate o piso é o próprio achado 3.

## Consequências

- **(+)** A disciplina de edge vira **invariante verificável**: nenhuma aposta autorada com `edge_pct < piso` é persistida/exibida/entra no Yield. Fecha o achado 3.
- **(+)** **Sinergia com o harness (#484):** o gate limpa o Yield de apostas sub-piso, e a calibração (`/admin/calibration`) mede o modelo com um universo de recomendações honesto. As rows rebaixadas viram `pass` mas seguem alimentando o PSO/calibração (o `modelProbPct[over]` persiste em pass).
- **(+)** **Custo zero de dados:** sem migration, sem coluna; reusa o campo `minEdgePp` existente, a lógica de pass-shape e o edge já computado.
- **(−) Risco: assimetria 1X2** (edge de-vigado ≠ `confidence − implícita` do prompt) — um lado que o LLM achou apostável pelo `confidence` pode gatear pelo edge de-vigado. Aceito: o edge de-vigado é o número honesto (ADR 0018) e é o que a gente aciona; o prompt-rule fica como guia soft.
- **(−) Risco: o "best bet" pode virar "nenhuma aposta"** num jogo onde nenhum mercado bate o piso — resposta honesta; a badge "Melhor aposta" é suprimida (Decisão 5).
- **(−) Risco: rebaixamento silencioso** (uma rec vira pass sem marcador explícito). Mitigado pela reconstrutibilidade (rationale + PSO); um flag explícito é follow-up.
- **(±)** `predict.ts` ganha o gate; o campo `minEdgePp` ganha um terceiro consumidor (gate) além de prompt+view. Partition segue sem declarar o piso (fallback `?? MIN_EDGE_PP`); só scorer/assist o declaram (8, agora via `SCORER_MIN_EDGE_PP`).
- **(não-escopo, registrado)** Kelly (rec. 7) e DC-MLE (rec. 6) seguem gated na calibração; o flag de downgrade e o prompt-lê-descriptor completo ficam como follow-ups.
