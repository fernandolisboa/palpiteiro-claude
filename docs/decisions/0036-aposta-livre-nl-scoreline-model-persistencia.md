# ADR 0036 — "Aposta livre": input NL híbrido + modelo de placar determinístico + persistência/settlement — emenda o ADR 0034

## Status

Accepted (2026-07-04) — issue #451 (ADR-first; Report 04 rec. 1; plan-gate de 2 rodadas: 3 lentes adversariais → rework → re-verify). **Emenda o ADR 0034** ("Analise minha aposta", leitor de valor selection-pinned): preserva-lhe TODOS os escudos regulatórios e o dual-channel, e relaxa deliberadamente **quatro** itens — os três que aquele ADR deferiu/excluiu (múltipla, props sem cartucho, persistência) mais o **input NL na frente do boundary** (ver Decisão 7). **Vive no registro Análise / Recomendação** (ADR 0028), onde números de valor são legítimos; **NÃO** roteia pelo firewall da manchete e **NÃO** o enfraquece (zero novos callers de `containsValueLanguage`, `lib/ai/palpites/value-language-guard.ts:32`). Especifica também o módulo compartilhado `lib/quant/scoreline-model.ts` (issue #452), que o arco IA-científica (Report 03, item 3) consumirá depois sob ADR próprio.

> **Escopo:** produto + IA + dados (3 tabelas novas, migration única ≥0041 — o sidecar de attempts fica deferido, ver Decisão 5 e Consequências) + 1 módulo puro novo (`lib/quant/`) + 1 cartucho de parse novo (`lib/ai/bet-parse/`). Este ADR registra DECISÕES e porquês; o plano de build vem nas issues downstream. Onde houver tensão entre **UX fluida** e **gradear a aposta certa**, a resolução é **sempre** a confirmação explícita (prefer-skip-over-silent-wrong). Onde houver tensão entre **cobertura** e **honestidade do número**, a resolução é **sempre** rotular a fonte ("modelo simplificado") ou dizer "não avalio" — nunca apresentar um número Poisson como número de cartucho, nunca fabricar. **FORA do escopo:** o seam `predict.ts` step-6 (fatos estruturados Poisson no prompt — item 3/Report 03) fica para um ADR futuro; este ADR não autoriza tocar `lib/ai/predict.ts`.

## Contexto

O grade-my-bet **v1** (#412, ADR 0034) está MERGED + LIVE: a action `gradeMyBet` (`app/actions/predictions.ts:814-1062`) valida um input estruturado (`GradeMyBetInputSchema`, `lib/view/grade-my-bet-input.ts`), gateia linha-modelável ANTES de gastar, lê cache-first via `getLatestPredictionForPin`, e só no MISS passa por `checkAnalysisRateLimit` + `ensureOddsSnapshotsFresh` + `predict()`. O mapper puro `toGradeMyBetView` (`lib/view/grade-my-bet.ts:69`) deriva a leitura de 3 strings template por `Math.sign(EV)` (`VALUE_READING`), com kinds `grade-coberto`/`nao-avalio`/`degradado-sem-snapshot`. A UI é um picker `market → selection → linha → odd` (`components/grade-my-bet.tsx`).

O v1 funciona, mas tem um problema-raiz de UX: **a direção da tradução**. O usuário precisa traduzir a aposta mental dele ("Palmeiras 2 a 0", "o mandante marca primeiro", "mais de 1 gol no 1º tempo", uma combinada no mesmo jogo) para a taxonomia interna marketKey→selectionKey→linha — e a taxonomia só cobre o que tem cartucho + board de odds. A ironia: **o sistema já entende quase todas essas formas de aposta no outro lado** — a síntese de palpite emite `exact_score`/`margin`/`clean_sheet`/`first_half_score`/`first_to_score`, e as **regras puras de settlement de todas elas já rodam em produção** (`PALPITE_SETTLEMENT_RULES`, `lib/settlement/rules/palpite-dispatch.ts`; regras `(params: unknown, resultData: PalpiteResultData) => "won"|"lost"` que lançam `SettlementError` → PENDING), mais cartões via extração web (ADR 0033, coverage-gated).

O que falta não é compreensão nem settlement — é: **(1)** um boundary de input que aceite a aposta como o usuário fala; **(2)** um modelo de precificação para props derivados de placar que nenhum cartucho/board cobre; **(3)** persistência, para a aposta ter ciclo de vida (graded → pendente → acertou/errou) em vez de evaporar. E o dado para (2) **já chega do provider e é descartado**: os fluxos que buscam standings (`lib/ai/predict.ts:260`, `lib/ai/palpites/index.ts:147`) recebem `NormalizedStandingTeam.homeSplit/awaySplit` com `{played,wins,draws,losses,goalsFor,goalsAgainst}` por mando em ~15–20 jogos (`lib/providers/sports-data/types.ts:133-134`), mas `findStanding` hoje só aproveita position/points (`lib/ai/palpites/cartridges/cartridge.ts:384`).

Por que ADR (e não direto pra build): (1) o NL introduz um **novo modo de falha** — misparse silencioso gradearia uma aposta DIFERENTE da que o usuário quis; (2) props exigem um **modelo de probabilidade novo** (primeira probabilidade de modelo que NÃO vem de LLM no repo — Report 03, achado 1); (3) múltipla exige decisão de **correlação** (o motivo exato do defer no 0034 §1); (4) persistência de **intenção de aposta** muda o perfil regulatório/LGPD da superfície; (5) `lib/quant` terá **dois consumidores** (itens 3 e 4) — a espec compartilhada precisa ser fixada uma vez.

## Decisão

**1. INPUT HÍBRIDO: NL na frente, chips estruturados confirmáveis atrás — o slip confirmado é o contrato, nunca o texto cru.** Na aba "Minha aposta" (`components/match-analysis-tabs.tsx`, `role=group`/`aria-pressed`, renderizada só quando o jogo é analisável — pré-jogo `scheduled`), o usuário digita texto livre (*"Palmeiras 2x0, casa marca primeiro, odd 8.50"*) ou toca chips de exemplo. Um parse LLM (Decisão 2) devolve pernas tipadas; a UI **ecoa de volta como chips de perna editáveis** — cada chip com badge de settleability ("conferimos após o jogo" / "não conferimos escanteios") — e o picker v1 vira **editor por-chip** (mesmo vocabulário de campos, reaproveitado). **Nada é gradeado até o usuário confirmar.** O slip Zod-validado confirmado é a ÚNICA coisa que entra no motor de valor — o NL é açúcar na FRENTE do boundary fail-closed do 0034 §7, não um buraco através dele. O texto livre é **capado em ~280 caracteres no boundary Zod do parse** (rejeição com mensagem clara): fecha o custo pior-caso do parse E minimiza o `rawInput` persistido (LGPD — auditoria de misparse não precisa de mais que o tamanho plausível de uma aposta). Racional das duas alternativas mortas: builder estruturado puro é o v1 e a fonte da tediosidade (e nunca enumera props/placares/combos sem virar planilha); NL puro sem confirm tem como pior modo de falha um misparse silencioso ("over 2.5" ouvido como "under 2.5") que produz veredito confiante, plausível e ERRADO — o anti-padrão que **prefer-skip-over-silent-wrong** existe pra matar. O confirm converte incerteza de parse em verdade verificada pelo usuário. Pernas que o Zod rejeitar no parse são **dropadas com aviso visível** ("não entendi: *<trecho>*" / "não avaliamos linha 2.0 — use 1.5 ou 2.5"), nunca silenciosamente — a ausência é visível no echo e o confirm continua obrigatório.

**2. Cartucho de parse Haiku em `lib/ai/bet-parse/` — Zod `.strict()`, `bet_parse_v1`, logado em `ai_calls`.** O parse é um cartucho novo seguindo a forma do `PalpiteCartridge` (`lib/ai/palpites/cartridges/cartridge.ts`; tool via `toToolDef`; output Zod `.strict()`): system prompt versionado `promptVersion = "bet_parse_v1"` (proveniência em `ai_calls` é a `promptVersion` — a tabela não tem coluna `purpose`), output = **união discriminada `.strict()` de pernas** (`BetLegSchema`: kinds de mercado `over_under`/`match_result`/`btts`/`double_chance` + kinds de prop `exact_score`/`margin`/`clean_sheet`/`first_half_score`/`first_half_over_under`/`first_to_score`/`cards`/`corners`, cada um com `params` próprio range-checked) + odd combinada opcional + odds por-perna opcionais (parse de vírgula PT-BR, `>1`, como 0034 §7d). Regras duras do schema: **(a)** a linha de QUALQUER total (`over_under`, `first_half_over_under` — params `{line}`) é restrita a **meio-gol (k+0.5)**, range-checked; linha inteira (`over 2.0` — push possível) ou de quarto (`2.25` — meio-push) → perna **dropada-com-aviso** no echo ("não avaliamos linha 2.0 — use 1.5 ou 2.5") — o espaço de resultado das pernas é binário won|lost (Decisões 5/6), e push/void é exclusão deliberada (Alternativa 14); **(b)** os `params` por kind **reusam os mesmos schemas Zod das regras de settlement** correspondentes — drift de shape entre boundary e regra deixaria a perna PENDING pra sempre via `SettlementError`. **Mecânica do drop-por-perna:** o tool schema devolve um envelope `{legs, comboUserOdd?, ...}` com `legs: z.array(z.unknown())`; cada item é validado **individualmente** (safeParse) contra a união `.strict()` — item inválido (kind alucinado, params fora de range, linha não-.5) vira o aviso da Decisão 1 e é dropado, e o slip segue com as pernas válidas; o parse inteiro só falha (`parse-falhou`) se o envelope for malformado ou `legs` vier vazio. Modelo: **Haiku 4.5** via `MODEL_REGISTRY` (`lib/ai/models.ts:43`, $1/$5 MTok — os palpites já rodam em Haiku a ~US$0.002/set; um parse capado a 280 chars é da mesma ordem ou menor). A chamada passa pelo **seam `AIProvider`** (ADR 0027; contrato em `lib/ai/providers/types.ts`, `getProviderForModel` em `lib/ai/providers/index.ts:18`) e loga em `ai_calls` via `lib/ai/ai-call-logging.ts` + `calculateCost` — **nunca** SDK direto (CLAUDE.md), e **não** por `lib/ai/predict.ts` (que é o motor de análise de mercado e insere `predictions`; parse não é análise — o precedente sancionado de segunda porta é `lib/ai/palpites/`, mesma disciplina seam+logging).

**3. GRADING EM DOIS CAMINHOS, roteados por kind×gate e rotulados pela fonte — cartucho onde o gate passa, modelo determinístico onde não.**
   - **CAMINHO A — kinds de mercado DENTRO do gate audiência∩liga e com linha na escada do cartucho:** **reusa o core cache-first do #412 verbatim** — mesma cadeia `getLatestPredictionForPin` (HIT = zero LLM, zero `ai_calls`) → MISS = `checkAnalysisRateLimit` + `ensureOddsSnapshotsFresh` + `predict()` → re-lê → ainda MISS = "não avalio" (`app/actions/predictions.ts:814-1062`). Toda a matemática dual-channel do 0034 §2/3 carrega intacta (EV/break-even/lucro na odd do usuário; edge SÓ no board de-vigado próprio; a odd do usuário NUNCA entra no Σ1/odd). O rate-limit é cobrado **por perna cara no MISS** (como o fan-out do `analyzeMarkets` cobra por mercado), nunca no HIT. `gradeSource = 'cartridge'`, `pinnedPredictionId` aponta a prediction usada. **Dentro do gate, A é o único caminho:** MISS pós-`predict()` ou falha transiente NUNCA rebaixa pra B — dois números de fontes diferentes pra mesma linha é landmine que este ADR não abre; o que faltou fica registrado por perna (`gradeStatus`, Decisão 5).
   - **CAMINHO B — pernas derivadas de placar sem cartucho aplicável:** os props (`exact_score`, `margin`, `clean_sheet`, `first_half_score`, `first_half_over_under`, `first_to_score`), totais em linha k+0.5 fora da escada modelada, **e os kinds de mercado que são predicados de placar quando FALHAM o gate audiência∩liga** (ex.: 1X2 pra não-admin enquanto não gradua; btts/dupla chance fora da Copa) — **`lib/quant/scoreline-model.ts`** (Decisão 9), distribuição **double-Poisson determinística**, zero LLM, **nenhum endpoint/provider novo** — mas com **call-site novo**: a action de grade orquestra `provider.getStandings()` (cacheado) ela mesma, com caminho de falha próprio (hoje quem busca standings são `predict()` em `lib/ai/predict.ts:260` e a síntese de palpites em `lib/ai/palpites/index.ts:147`; `gradeMyBet` não busca). λ estimados dos **splits casa/fora** (`homeSplit`/`awaySplit`, `types.ts:133-134` — GF/GA em ~15–20 jogos por mando, hoje descartados) com **shrinkage** pro prior da liga (forma pinada na Decisão 9); `summarizeForm` (`cartridge.ts:357`, janela ~5 overall) entra só como complemento, nunca como fonte primária (n=5 é ruidoso demais). **Escada de degradação (pinada):** **(i)** splits presentes com `played ≥ 5` nos DOIS times → Maher multiplicativo + shrinkage; **(ii)** splits ausentes ou `played < 5` → λ = prior de liga puro, rótulo "modelo simplificado (dados limitados)"; **(iii)** standings indisponível (provider down, liga sem tabela) → pernas B viram "não avalio" (prefer-skip — NUNCA λ fabricado). **Copa/mando neutro (mata-mata):** split casa/fora perde o sentido (e o adapter api-football os deixa undefined na World Cup) — usar a **média dos dois splits (casa+fora) por time** quando existirem, senão (ii)/(iii). A **média da liga** (normalização do Maher + prior do shrinkage) vem da MESMA tabela de standings, computada pelo adapter na fronteira do consumidor a partir das colunas **overall** (Σ `goalsFor` / Σ `played`, `types.ts:126-131`) — deliberadamente NÃO dos splits, pra continuar computável quando os splits faltam na tabela inteira (World Cup, degrau (ii)) — nenhuma fonte extra. Formas fechadas/leitura da matriz: `P(placar h–a)`, `P(margem≥k)`, `P(clean sheet)=e^{−λ_adv}`, `P(over L)`, 1º tempo via **time-share** (λ_1T = κ·λ, κ≈0.45 de literatura — precifica `first_half_score` E `first_half_over_under`), `P(casa marca primeiro)=λ_h/(λ_h+λ_a)·(1−e^{−(λ_h+λ_a)})`. Todo número do caminho B é **rotulado "modelo simplificado" na UI e no dado** (`gradeSource = 'scoreline_model'`), **nunca apresentado como número de cartucho**. **Perna B não tem canal de edge/implícita:** sem board de mercado completo não há de-vig (ADR 0018) — exibe probabilidade do modelo + EV/break-even/lucro na odd do usuário, e edge = "—" SEMPRE; **PROIBIDO derivar pseudo-implied de `1/userOdd`** (é o `1/odd` cru que o CLAUDE.md veta: margem de UM book, sem Σ1/odd pra normalizar) — teste pinado na build. Caminho B é grátis (determinístico) — não consome rate-limit de análise.
   - **Tabela de roteamento (kind → caminho):** `over_under` → **A** se o gate passa e a linha está na escada do cartucho; **B** pra qualquer outra linha k+0.5 ou gate falho. `match_result`/`btts`/`double_chance` → **A** se o gate passa; **B** se falha. `exact_score`/`margin`/`clean_sheet`/`first_half_score`/`first_half_over_under`/`first_to_score` → sempre **B**. `cards`/`corners` → **none** (aceita-não-gradeada, bullet abaixo). O roteamento elimina a incoerência solo-vs-combo ("Palmeiras vence" ganharia número dentro da combinada e "—" solo, vindo da mesma matriz) e **não contorna o gate de graduação**: o gate governa números de CARTUCHO; o caminho B entrega número de OUTRA fonte, rotulado, sem edge, e nunca sombreia o cartucho dentro do gate (Alternativa 15).
   - **Fora dos dois caminhos** (`cards`, `corners` — o modelo de placar não os precifica): a perna é **aceita** no slip (echo/track de intenção), mas **não gradeada** ("não avaliamos cartões/escanteios como número", `gradeSource='none'`, `gradeStatus='not_covered'`) — 0034 §8 fail-closed carrega; `cards` continua settleable (Decisão 6). Cap **`MAX_LEGS = 4`** por slip.
   - Os grades são **CONGELADOS no write** (`modelProbPct` persistido por perna; render lê o persistido, nunca recomputa) — carrega o landmine persisted-vs-recompute do 0034 (dois números do mesmo lado na mesma tela é inaceitável).

**4. COMBINADA SAME-GAME: probabilidade conjunta por SOMA sobre a matriz de placar — NUNCA multiplicação ingênua.** Toda perna que é um **predicado sobre o placar final** (`exact_score`, `margin`, `clean_sheet`, totais, 1X2, btts, dupla chance) torna a probabilidade conjunta **exatamente computável**: `P(combo) = Σ` das células da matriz de placar que satisfazem TODOS os predicados — capturando a correlação do mesmo jogo que a multiplicação de marginais destrói. Isso **dissolve** a objeção que fez o 0034 §1 deferir a múltipla (o motor só tinha marginais por mercado; a matriz É a distribuição conjunta). Regras duras: **(a)** a conjunta vem SEMPRE de **uma única distribuição coerente** — a matriz do modelo simplificado — mesmo quando uma perna individual foi gradeada pelo CAMINHO A (misturar marginal de cartucho com célula Poisson somaria medidas diferentes); a linha combinada é portanto sempre rotulada "modelo simplificado". **Invariante de coerência de tela (pinado):** o card da combinada exibe o joint **E as marginais Poisson das pernas participantes** — todas lidas da MESMA matriz, então `joint ≤ min(marginais)` é garantido matematicamente; cada chip de perna mantém o número da SUA fonte no próprio card (cartucho onde A, Poisson onde B). **Nunca** renderizar um joint ao lado de marginal de OUTRA fonte sem a marginal Poisson junto — é a forma dura do landmine "dois números do mesmo lado na mesma tela"; **(b)** pernas que NÃO são predicados sobre o placar final — `first_to_score` e as de 1º tempo (`first_half_score`, `first_half_over_under` — vivem em processo temporal / matriz-κ própria) — ficam **fora do joint**: grade por-perna normal + linha fixa **"combinada não avaliada"**; idem pernas não gradeáveis (`cards`/`corners`) **e pernas predicado-de-placar que ficaram sem grade no confirm** (`gradeSource='none'`, ex. rate-limited) — o joint só computa quando TODAS as pernas de placar do slip têm grade; qualquer uma de fora derruba a linha pra "combinada não avaliada" (nunca precificar um combo diferente do apostado); **(c)** EV da combinada = `computeEvPerUnit(jointProbPct, comboUserOdd)` só quando o usuário deu a odd combinada E o joint é computável; sem uma das duas, exibe só a probabilidade conjunta ou a linha "combinada não avaliada" — nunca um EV parcial.

**5. PERSISTÊNCIA: 3 tabelas novas em migration única (≥0041); grade roda NO confirm; slip imutável depois.**
   - **`bet_slips`** — `id`, `matchId`, `userId`, `rawInput` **nullable** (o texto NL cru, capado ~280 chars, pra auditoria de misparse; null = slip montado só pelo editor), `parseAiCallId` **nullable** (FK pra `ai_calls`; null idem), `comboUserOdd` **nullable** (a odd combinada que o usuário citou), `jointProbPct` **nullable** (congelado no grade), `createdAt`. As colunas de combo entram já na migration da Fase 1 mesmo sendo consumidas na Fase 3: nullable e baratas, evitam churn de migration.
   - **`bet_legs`** — `id`, `slipId`, `kind` (enum da união da Decisão 2), `params` jsonb **narrowed por Zod** por kind (reusando os schemas das regras de settlement, Decisão 2), `userOdd` **nullable** (usuário pode ter dado só a combinada), `modelProbPct` nullable (congelado no grade), `gradeSource` (`cartridge` | `scoreline_model` | `none`), **`gradeStatus`** (`graded` | `not_covered` | `no_data` | `rate_limited` | `degraded_no_snapshot` — o motivo do estado da perna. Sem número ⟺ `not_covered`/`no_data`/`rate_limited`, e só nesses `gradeSource='none'`. **`degraded_no_snapshot` NÃO é caso sem-número** — segue o v1 (`lib/view/grade-my-bet.ts:148-167`): `gradeSource='cartridge'`, `modelProbPct` + EV/break-even/lucro congelados normalmente e só o edge = "—", porque o canal odd-do-usuário independe do board (§2/§3). O **par** (`gradeSource`, `gradeStatus`) determina o estado por-perna da Decisão 10), `pinnedPredictionId` nullable, `settleable` **boolean derivado DO KIND** no código (mapa estático estilo `deriveSettleable`, **NUNCA do LLM**).
   - **`bet_leg_outcomes`** — `legId` **UNIQUE**, `result`, `resultData`, `settledAt`, **`overrideByUserId` nullable** (FK users, `onDelete: set null`) — espelho FIEL de `palpiteOutcomes` (`db/schema.ts:544`): o CLAUDE.md exige settlement idempotente COM override manual, e essa coluna é onde a proveniência do destravamento de pendências vive.
   - **Índices e FKs:** `bet_slips` ganha `(userId, createdAt desc)` (histórico) e `(matchId)`; FKs `restrict` pra users/matches. `bet_legs`: FK `slipId` **cascade** + índice. `bet_leg_outcomes`: `legId` UNIQUE **cascade**. A query de pendências do settlement espelha `getPendingPalpiteSettlements` (`lib/db/queries/palpites.ts:286`): pernas `settleable=true` sem outcome, de jogos `finished` — os índices acima existem PRA ela e pro histórico, não decorativos.
   - **Sem sidecar de attempts no v1:** `bet_leg_settlement_attempts` (espelho de `palpiteSettlementAttempts`) fica **deferido** — o attempt-cap só protege o caminho de retry pago WEB_GROUNDED de `cards`, e `CARDS_COVERED_LEAGUES` está vazio hoje (inerte). A tabela aditiva entra como pré-requisito do flip da cobertura de cards pra pernas de usuário (Consequências).
   - **Ciclo de vida:** o slip só é persistido **no confirm** (parse abandonado não deixa órfão; `rawInput`/`parseAiCallId` viajam no confirm). **O grade roda NO confirm:** falha transiente persiste o estado em `gradeStatus` — rate-limit exaurido = sem número (`gradeSource='none'`); `degraded_no_snapshot` = número e EV normais com edge "—" (regra do bullet `bet_legs` acima, espelhando o v1) — e **não existe re-grade posterior** (slip imutável); avaliar de novo = novo slip, re-passando por todos os gates. Após confirm, slip e pernas são **imutáveis** — corrigir = novo slip (espelha "nunca mutar predições passadas", CLAUDE.md). Status do slip é **derivado em leitura** das outcomes das pernas (won = todas won; lost = alguma lost; pendente = resto; pernas `settleable=false` deixam a combinada como "não conferida") — nenhuma coluna de status denormalizada. **Não se toca** em `predictions`/`ai_calls`/`palpites` (a partição do ADR 0028 fica). Numeric→string do Drizzle: `userOdd`/`modelProbPct`/`comboUserOdd` passam por `Number()` na fronteira de view, como hoje.

**6. SETTLEMENT: `lib/settlement/settle-user-bets.ts` espelha `settle-palpites.ts` e REUSA as regras puras verbatim; settleable derivado do kind.** Orquestrador novo `settleUserBetLegs(now)` com a MESMA forma de `settlePendingPalpites` (`lib/settlement/settle-palpites.ts`): só liquida jogo `finished` **com `regulationScore`** (90', sem prorrogação/pênaltis), monta o **mesmo `PalpiteResultData`** (`lib/settlement/palpite-result-data.ts:74`), idempotente via insert-if-absent + UNIQUE `legId`, summary `{considered, settled, alreadySettled, skipped, errors, byResult}`, invocado no mesmo cron.
   - **Kinds de prop com regra existente** (`exact_score`, `margin`, `clean_sheet`, `first_half_score`, `first_to_score`, `cards`): **reusam `PALPITE_SETTLEMENT_RULES` verbatim** — as regras são puras `(params: unknown, resultData) => "won"|"lost"`, sem acoplamento de tabela (`palpite-dispatch.ts`); `SettlementError` → PENDING visível (prefer-skip).
   - **Regras puras NOVAS na mesma forma**, registradas num dispatch próprio que compõe com o existente: **(a)** kinds de mercado (`over_under`, `match_result`, `btts`, `double_chance`) — predicados triviais sobre `regulationScore`; o `over_under` de slip liquida com linha **garantidamente k+0.5** (o boundary da Decisão 2 exclui linha inteira), então é binário sem push — diferente da regra do domínio de predições (`lib/settlement/rules/over_under.ts:30`), que precisa de push pra linha inteira; **(b)** `first_half_over_under` — trivial sobre `halftimeHomeScore + halftimeAwayScore` vs linha k+0.5, mesma forma `(params, resultData) => won|lost`; halftime ausente → `SettlementError` → PENDING (irmã da regra de placar exato do intervalo, `lib/settlement/rules/first_half_score_palpite.ts`).
   - **Dependências de dado espelham o existente:** kinds de 1º tempo exigem `halftimeHomeScore`/`halftimeAwayScore` (ausente → PENDING); `first_to_score` é EVENT_BACKED (`getFixtureEvents`; ausente → PENDING); `cards` é WEB_GROUNDED (`extractCardCount`, coverage-gated por `CARDS_COVERED_LEAGUES` — vazio hoje ⇒ inerte, perna fica pendente até a cobertura ligar; ligar a cobertura pra pernas de usuário pressupõe o sidecar de attempts, Decisão 5).
   - **Escanteios: honestamente NÃO-liquidável** (achado empírico do settle-from-web: tabelas JS-rendered, variância ±1) — `settleable=false` derivado do kind, badge "não conferimos escanteios" **no confirm** (expectativa setada antes, não depois do jogo), a perna **nunca entra na query** de settlement.

**7. ESCUDOS DO 0034: o que carrega VERBATIM e os QUATRO relaxamentos deliberados.**

Aposte com responsabilidade, só o que você pode perder, e nunca para recuperar perdas. O **pipeline da manchete fica intocado**.
   - **Relaxamentos deliberados — QUATRO** (os três que o 0034 deferiu/excluiu + um de fronteira de input): **(i)** 0034 §1 "parlay fica de fora (v2) — exige probabilidade conjunta que o motor não tem" → a matriz de placar É a distribuição conjunta; múltipla same-game entra via joint-sum (Decisão 4), e SÓ nela — a objeção original continua válida (e a múltipla continua recusada) pra pernas fora da matriz. **(ii)** 0034 §8 "cobertura = só cartuchos com `selectionProbs`" → o CAMINHO B estende a props derivados de placar (e a kinds de mercado fora do gate) com fonte determinística rotulada, sem fingir cobertura de cartucho. **(iii)** 0034 escopo "sem dados/migration novos", nada persistido → persistência com ciclo de vida (Decisão 5), porque sem ela não há histórico, settlement, nem loop de calibração. **(iv)** **input NL na frente do boundary** → o 0034 assumia input exclusivamente estruturado e vetava sub-chamada LLM nova no fluxo (§5); o parse `bet_parse_v1` relaxa isso **só na FRENTE do boundary** — uma chamada Haiku pré-boundary, via seam ADR 0027 + `ai_calls` (precedente sancionado: `lib/ai/palpites/`). O §7 continua sendo o contrato **NO CONFIRM**: o que entra no motor de valor é exclusivamente o slip Zod fail-closed re-validado server-side, e o caminho de GRADE continua sem sub-chamada LLM nova (`predict()` só no MISS).

**8. CUSTO E RATE-LIMIT: parse e criação de slip com limiters próprios; slots de análise por perna cara; HIT e caminho B grátis.** Um grade de slip custa no pior caso: 1 parse Haiku (~ordem de US$0.002, input capado a ~280 chars, sempre logado em `ai_calls` com custo via `calculateCost`) + `predict()` cheio por perna de cartucho em MISS. Decisões: **(a)** o parse ganha um **limiter próprio** no padrão de `lib/rate-limit.ts` (fixedWindow, default **`RATE_LIMIT_BET_PARSE_PER_DAY=30`** por usuário, env-tunável, **fail-closed pra não-admin**) — **não** consome `checkAnalysisRateLimit`: cobrar um slot de análise (20/dia) por um texto digitado errado seria mis-escalado. O fail-closed **diverge deliberadamente** do fail-open do limiter de palpites (`checkPalpitesRateLimit`, `lib/rate-limit.ts:164` — fail-open porque palpite é auto-run interno): o parse é gatilhado por **input arbitrário digitado pelo usuário** — spammable — então sem KV o default seguro pra não-admin é negar (mesmo racional do ADR 0023); **(b)** cada perna de CAMINHO A em MISS consome `checkAnalysisRateLimit` individualmente (é gasto real, espelha o fan-out do `analyzeMarkets`); HIT não consome nada. **Exaustão no meio do slip:** pernas já gradeadas MANTÊM seu número; as restantes persistem com `gradeStatus='rate_limited'` e sem número (estado por-perna, Decisão 5) — sem rollback, sem re-grade; o caminho B das demais pernas continua grátis e grada normal; **(c)** CAMINHO B e joint-sum são determinísticos — grátis, sem limiter de análise; **(d)** `MAX_LEGS = 4` limita o blast radius de um slip; **(e)** re-grade do mesmo slip não existe (slip imutável) — nova avaliação = novo slip, que re-passa pelos gates; **(f)** **cap de criação de slips**: limiter próprio fixedWindow **no confirm** (default **`RATE_LIMIT_BET_SLIPS_PER_DAY=30`** por usuário, env-tunável, fail-closed pra não-admin — mesmo racional do parse: gatilho é ação arbitrária do usuário), cobrindo TAMBÉM slips editor-only, que não passam pelo parse limiter — fecha o único caminho não-metrado que restaria (escrita de rows + `getStandings` por grade Poisson-only + crescimento do pending-set do cron).

**9. `lib/quant/scoreline-model.ts` — módulo PURO, determinístico, consumer-agnóstico (issue #452; construído UMA vez pra itens 3 e 4).** `lib/quant/` não existe hoje; nasce com contrato fixado aqui:
   - **Pureza dura:** síncrono, determinístico, ZERO imports de `@/lib/db`, `@/lib/ai`, `@/lib/providers` (nem types) — os tipos de input são **estruturais próprios do módulo** (ex.: `SplitGoalRates = {played, goalsFor, goalsAgainst}` por mando + baseline de liga); cada consumidor adapta na SUA fronteira (a aposta livre adapta de `NormalizedStandingTeam.homeSplit/awaySplit`, `types.ts:133-134`, e computa o baseline de liga da mesma tabela — Decisão 3).
   - **API:** `estimateLambdas(input) → {lambdaHome, lambdaAway, meta}` — forma multiplicativa de Maher (ataque do split casa do mandante × defesa do split fora do visitante, normalizados pela média da liga, que é INPUT estrutural) com **shrinkage de pseudo-contagem fixa** pro prior da liga, forma pinada: **`λ_post = (n·λ_obs + k·λ_liga)/(n + k)`**, com `k = SHRINKAGE_PSEUDO_GAMES = 5` jogos-equivalentes como default documentado — o valor exato pode ser ajustado na build com teste golden, mas a FORMA e o default ficam neste ADR (sem eles os goldens de λ não são escrevíveis); `meta` sinaliza a fonte/degrau da escada (splits | prior-puro); `scorelineMatrix(λh, λa, opts) → Matrix` — double-Poisson truncada (MAX_GOALS≈10, renormalizada), com correção **Dixon-Coles τ** nas células (0,0)/(1,0)/(0,1)/(1,1) (ρ≈−0.10 de literatura) embutida e **guarda de validade: τ ≥ 0 nas 4 células** (clamp documentado — λ absurdo vindo de um adapter bugado não pode virar célula negativa silenciosa) — implementação ÚNICA pros dois consumidores; **readers sobre a matriz** (nunca sobre λ direto, pra τ ser drop-in): `pScoreline`, `pMarginAtLeast`, `pCleanSheet`, `pOverUnder`, `pBtts`, `p1X2`, grid `cs16`, `jointProbability(matrix, predicates[])`; módulo de 1º tempo via time-share κ (precifica `first_half_score` e `first_half_over_under`); `pHomeScoresFirst` em forma fechada.
   - **Contrato de teste:** matriz soma ≈1 e **todas as células ≥ 0**; λ clampado a range são (ex.: [0.2, 4.5]); readers batem as formas fechadas com τ=0 (as fórmulas da Decisão 3 são os oráculos); casos golden de λ (dependem do `k` pinado acima); propriedades de monotonicidade.
   - **Consumidores:** a aposta livre (CAMINHO B + joint) consome JÁ; o item 3 (fatos estruturados no `buildPredictionInput`, seam `predict.ts` step-6, política de blend, bump de prompt) consome DEPOIS **sob ADR próprio** — este ADR fixa só o módulo e sua pureza, não a integração com o motor de análise.

**10. ROLLOUT FASEADO com tracer bullet; critério de aceite e loop de calibração.**
   - **Fase 1 (tracer):** a perna **placar-exato end-to-end** — parse → confirm → grade Poisson → persist → settle → badge no histórico. Escolhida porque atravessa TODA costura nova (cartucho de parse, `lib/quant`, 3 tabelas, `settle-user-bets.ts`, chips de UI) reusando uma regra de settlement que já roda em produção. **Aceite da Fase 1:** *"Palmeiras 2x0, odd 9.00"* digitado numa match page analisável vira chip confirmável com badge "conferimos após o jogo"; no confirm, persiste slip+perna com `modelProbPct` do modelo rotulado "modelo simplificado", EV@odd-do-usuário e disclaimer §3 verbatim; standings indisponível no momento do grade → "não avalio" visível com o motivo (escada da Decisão 3); após o jogo, o cron liquida via regra `exact_score` existente, idempotente; jogo sem `regulationScore` fica PENDING visível.
   - **Fase 2:** demais kinds do CAMINHO B (incl. roteamento gate-failed e `first_half_over_under`) + integração CAMINHO A (core #412) + editor por-chip completo.
   - **Fase 3:** combinada joint-sum + odd combinada + seção "Minhas apostas" (histórico: **paginação cursor por `createdAt desc`, ~20 por página**, status derivado no SELECT via agregação das outcomes).
   - **Loop de calibração (critério de permanência, Report 04 rec. 8):** `modelProbPct` congelado por perna + outcomes liquidadas dão calibração de graça. **Baseline pinado:** a MESMA matriz com λ = média da liga pros dois times (zero informação de time), avaliada nas MESMAS pernas liquidadas; **reporte por kind além do agregado** (Brier pooled sobre kinds heterogêneos deixa um modelo ruim em clean_sheet se esconder atrás de exact_scores); **janela = as primeiras ~100 pernas B liquidadas, depois rolling**. Se o modelo estiver pior que o baseline, **rebaixar a exibição de EV das pernas B pra probabilidade-only** (mantendo o rótulo) até recalibrar. É o substituto vivo dos backtests desescopados, coerente com a graduação D9.
   - **Estados de saída** (union discriminado, espelhando o contrato do v1): de slip — `parse-falhou` / `slip-invalido` / `combinada-nao-avaliada` / `nao-analisavel` / `limite-de-slips`; por perna — `grade-coberto` | `grade-modelo-simplificado` | `nao-avalio` | `degradado-sem-snapshot` | `rate-limited` (os por-perna persistem via `gradeSource`/`gradeStatus`, Decisão 5 — o histórico re-renderiza o estado real do confirm, nunca recomputa).

## Alternativas consideradas

1. **Builder estruturado puro (evoluir o picker v1 com mais dropdowns)** — rejeitado: é a fonte da tediosidade (a direção da tradução continua usuário→taxonomia) e não enumera props/placares/combos sem explodir o grid.
2. **NL puro, parse→grade sem confirmação** — rejeitado: misparse silencioso grada uma aposta DIFERENTE da intencionada com veredito confiante — anti-padrão prefer-skip-over-silent-wrong. O confirm é inegociável.
3. **Parse via `predict()` ou modelo caro** — rejeitado: `predict.ts` é o motor de análise de mercado (insere `predictions`, custa Sonnet); parse é extração estrutural barata. Haiku via seam AIProvider + `ai_calls` (padrão `lib/ai/palpites/`) mantém a disciplina sem o custo.
4. **Multiplicar probabilidades das pernas na combinada** — rejeitado: pernas do mesmo jogo são correlacionadas (over 2.5 e "2x0" são quase mutuamente exclusivos; over e btts, positivamente correlacionados); a multiplicação fabrica EV. Joint-sum sobre a matriz ou recusar.
5. **Precificar props elicitando probabilidade do LLM** — rejeitado: reintroduz número não-ancorado e não-medido (Report 03, achado 1) a custo por-perna; o double-Poisson é determinístico, grátis, testável e calibrável pelo próprio ciclo de settlement.
6. **Misturar marginal de cartucho com células Poisson no joint** — rejeitado: medidas de distribuições diferentes não compõem; a conjunta vem de UMA distribuição coerente (a matriz), rotulada — e a tela sempre mostra as marginais Poisson junto do joint (Decisão 4a).
7. **Reusar as tabelas `palpites`/`palpite_outcomes` pra pernas de usuário** — rejeitado: viola a partição do ADR 0028 (palpite é linha autorada pelo modelo, com Yield/graduação e firewall auditável; aposta do usuário é registro Análise) — misturar poluiria métricas e a auditoria guarded-vs-unguarded. Tabelas próprias, espelhando a FORMA (UNIQUE outcome, override manual).
8. **Não persistir (manter a evaporação do v1)** — rejeitado: sem persistência não há ciclo de vida, settlement, histórico, nem o loop de calibração que valida o modelo — os três motivos da feature.
9. **Settle escanteios best-effort via web** — rejeitado: achado empírico (tabelas JS-rendered, variância ±1 entre providers) o torna abaixo do settlement-grade; `settleable=false` derivado do kind, expectativa no confirm.
10. **`lib/quant` importando tipos de provider / fazendo fetch** — rejeitado: o módulo tem dois consumidores com fronteiras diferentes (aposta livre agora, `predict.ts` step-6 depois); tipos estruturais próprios + adapters nas fronteiras mantêm a pureza e a testabilidade.
11. **Gatear o parse pelo `checkAnalysisRateLimit`** — rejeitado: mis-escalado — um typo custaria 1 dos 20 slots diários de análise. Limiter próprio, barato, fail-closed.
12. **Slip editável pós-confirm / re-grade de perna que falhou** — rejeitado: espelha "nunca mutar predições passadas"; grades congelados + slip imutável preservam auditabilidade (misparse é auditável porque `rawInput` + chips confirmados coexistem; falha transiente fica registrada em `gradeStatus`, e re-avaliar é um slip novo pelos gates).
13. **Tornar slips compartilháveis via `/p/[id]`** — rejeitado: o registro público (ADR 0035) é manchete-only e firewall-bound; slip carrega EV/edge/odd/stake E `rawInput` (texto livre de usuário — que o ADR 0035 §3d garantia não existir no pipeline público). Nenhum caminho.
14. **Aceitar linha inteira/quarto de total com `push`/`void` no enum de outcome** — rejeitado: `bet_leg_outcomes` espelha `palpiteOutcomes` (won|lost), e o status derivado do slip e o joint-sum são binários — push exigiria EV push-aware, célula-de-push no joint e status ternário. Em vez disso o boundary restringe TODA linha de total a k+0.5 e dropa-com-aviso as demais (Decisão 2) — **exclusão deliberada da mesma família do handicap asiático**, que já está fora da união. O domínio de PREDIÇÕES continua com push onde precisa (`lib/settlement/rules/over_under.ts:30`, ADRs 0016/0018); a restrição é só do slip de usuário.
15. **Pernas de mercado fora do gate audiência∩liga → "não avalio"** (tratar o gate como teto duro também pro modelo simplificado) — rejeitado: a matriz já precifica exatamente esses predicados dentro de combinadas (Decisão 4) — a mesma perna "Palmeiras vence" ganharia número no joint e "—" solo, na mesma tela. O gate de graduação governa números de CARTUCHO; o CAMINHO B rotulado não o contorna (fonte distinta, sem edge, nunca sombreia o cartucho dentro do gate) — Decisão 3.

## Consequências

- **(+)** As "apostas dos sonhos" do dono viram input de primeira classe: placar exato, quem marca primeiro, total do 1º tempo, combinada same-game — com settlement reusado de produção e correlação tratada corretamente.
- **(+)** Primeira probabilidade de modelo **não-LLM** do repo, determinística e testável — e o ciclo de settlement vira harness de calibração de graça, alimentando o item 3 (Report 03) sem trabalho extra.
- **(+)** Reuso máximo: core cache-first do #412 verbatim (CAMINHO A), regras de settlement puras verbatim, dado de λ já entregue pelo provider (splits do standings hoje descartados em `cartridge.ts:384`), padrão de cartucho/logging/seam existente.
- **(+)** `lib/quant` construído uma vez serve os itens 3 e 4 (sinergia dos Reports 03/04); a espec de pureza evita o re-trabalho quando o item 3 chegar.
- **(−) Risco: misparse → aposta errada.** Mitigação: confirm obrigatório (Decisão 1) + validação por-item contra a união `.strict()` (Decisão 2) + echo em chips + drop-com-aviso + `rawInput` persistido pra auditoria.
- **(−) Risco: overconfiança do Poisson.** λ de janela-5 é ruído — por isso a fonte primária são os **splits casa/fora (~15–20 jogos)** + shrinkage de pseudo-contagem pinado, com escada de degradação explícita (prior de liga rotulado → "não avalio"); números arredondados, rótulo "modelo simplificado" onipresente, e o loop de calibração com baseline pinado e critério de rebaixamento (Decisão 10) como válvula.
- **(−) Risco: custo.** Parse Haiku ~US$0.002 logado, input capado a ~280 chars, limiter próprio 30/dia; MISS de cartucho cobrado por perna no rate-limit existente; `MAX_LEGS=4`; HIT e caminho B grátis; criação de slips capada em 30/dia — **inclusive o caminho editor-only/Poisson-only**, coberto pelo limiter de slips (Decisão 8f). Sem caminho de gasto não-metrado — nem de LLM, nem de escrita/fetch.
- **(−) Risco: frustração com perna não-liquidável.** Expectativa setada **no confirm** (badge por perna), nunca descoberta depois do jogo; escanteios aceitos-mas-não-conferidos em vez de rejeitados (track de intenção sem promessa).
- **(−) Risco regulatório: persistir intenção de aposta aprofunda a superfície de máxima intenção.** Todo escudo do 0034 carrega verbatim (Decisão 7), inclusive nas views novas de confirm/histórico; `rawInput` é texto livre do usuário — **capado (~280 chars), nullable**, fica autenticado/privado, nunca cruza fronteira pública, e entra no escopo LGPD de dados de uso (documentar em `/privacidade`); kill-path simples (delete do slip — cascade slip→legs→outcomes já modelado) fica pra build.
- **(−) Risco: armadilha de correlação.** Nunca multiplicar probs de pernas do mesmo jogo — joint-sum ou "combinada não avaliada"; teste pinado na build.
- **(−) Landmines que carregam do 0034:** odd do usuário fora do Σ1/odd (teste pinado); cache por linha exata (line-mismatch = MISS, nunca prob de linha vizinha); `impliedSumTarget`/`marketKind` threadados; drizzle numeric→string com `Number()` na fronteira; grades congelados no write, render nunca recomputa; **joint nunca renderizado sem as marginais Poisson das pernas participantes na mesma tela** (Decisão 4a); **perna B nunca exibe edge nem pseudo-implied de `1/userOdd`** (Decisão 3).
- **(±)** `settle-user-bets.ts` adiciona um segundo orquestrador ao cron de settlement — mesma forma, mesmo summary, mesmo prefer-skip; o custo é manter dois dispatches (props reusado + regras novas de mercado/1º-tempo) em vez de um.
- **(±)** O sidecar `bet_leg_settlement_attempts` fica **fora da migration v1** (o attempt-cap só protege o retry pago WEB_GROUNDED de `cards`, e `CARDS_COVERED_LEAGUES` está vazio — seria tabela inerte); fica registrado como **pré-requisito do flip da cobertura de cards** pra pernas de usuário. Já `comboUserOdd`/`jointProbPct` (consumidas só na Fase 3) entram na migration única da Fase 1: nullable e baratas, evitam churn de migration.
- **(±)** **Emenda ao CLAUDE.md na build:** a fronteira "toda chamada de LLM passa por `lib/ai/predict.ts`" passa a ler "toda chamada de LLM passa por `predict.ts` (análise de mercado) **ou pelos cartuchos sancionados por ADR** (palpites, bet-parse) — sempre via seam AIProvider (ADR 0027) + `ai_calls`, nunca SDK direto". Evita que cada ADR que abre porta sancionada (0030, 0032, agora este) re-tropece no texto categórico.
- **(não-escopo)** O seam `predict.ts` step-6 (Poisson como fatos estruturados no prompt, política de blend, `over_under_v2.2`) é o item 3 e fica pra ADR futuro — este ADR entrega o módulo que aquele ADR consumirá, nada mais.
